# ReliefOS 发布规范

## 版本与更新范围

- 发布版本由本仓 `configs/build-version` 的版本提交确定；标签使用 `v<版本>`，必须指向该版本提交的完整 SHA。
- 本次更新区间固定为 `(上一版本提交, 本次版本提交]`，即 `git log PREVIOUS..CURRENT` / `git diff PREVIOUS CURRENT`。起点不包含，终点包含；不能改用上次发布日期、最近一次构建、任意标签或只看最近一个提交。
- 例如 `5.1.0` 的更新是“改为 `5.0.0`”提交之后、直到“改为 `5.1.0`”提交的全部有效变更。下一版再以 `5.1.0` 的版本提交为起点。
- 必须记录起点版本及完整 SHA、终点版本及标签，并给出本仓 compare 链接。如果旧历史出现版本重置或无法唯一确定起点，向维护者提供具体提交选项并等待回答。
- 当前数字基础版本的格式为 `major.minor.patch`。预发布必须使用构建链实际支持的版本表示，并在 GitHub 标记 prerelease；不能只改标签、让产物仍报告另一个版本。

## 仓库边界

- ReliefOS Release 仅包括主仓自身源码、应用、系统配置、构建、测试及文档更新；排除 `kernel/reliefnt` 的实现与纯 gitlink 更新。混合提交只说明主仓部分。
- 两仓使用本文件下述相同章节顺序，但独立审阅历史、独立编写正文，不能复制另一仓的更新列表。
- 汇总区间内全部实际生效的更新，按用户或开发者可理解的功能归组。合并提交去重；中途添加后又撤销的功能不能当作最终交付。
- 不把“更新版本号到 x.x.x”、纯 merge、纯 gitlink 同步等机械条目列为更新。版本提交中若含实质修复或发布规范，仍应归入相应主题。
- compare 链接提供完整追溯，但不能代替对功能、兼容性和迁移影响的说明。

## Release 说明格式

正文以 `# 产品名 版本` 开始，按以下顺序使用二级标题，并归档到 `docs/releases/<版本>.md`：

1. `发布范围`：前一版本提交、当前标签、区间语义及仓库范围。
2. `更新内容`：完整覆盖本仓有效更新，按领域归组，省略机械提交条目。
3. `破坏性更新`：明确写“是”“否”或“尚未确认”；有破坏性变更时列明受影响接口、配置、路径、文件或工作流，不能因版本号是小版本而隐去。
4. `更新与迁移注意事项`：备份、升级步骤、重建要求、配置变化、旧数据和外部依赖注意事项；未验证的迁移路线必须明示。
5. `开发者提示`：构建条件、工具链、API/ABI/SDK、依赖与测试建议。
6. `验证与已知限制`：分开说明源码检查、编译、打包、QEMU、VMware、真实硬件；逐项写实际结果，未执行不是通过。
7. `获取与追溯`：源码/附件范围、校验和（若有二进制）、完整 compare 和相关文档链接。

## 提交、标签与 GitHub 发布

1. 检查两仓工作树，保留任务外修改和未跟踪文件，核实远端目标。只有用户明确授权才提交、推送、建立分支或发布。
2. 先完成版本、说明、发布规则和必要测试；主仓同时保持 `/etc/os-release` 的 `VERSION_ID` 与其发布版本一致。内核版本字符串与数字版本宏必须匹配，不修改 ABI golden 来掩盖失败。
3. ReliefNT 先在自己的仓库提交、验证和推送；父仓再更新 gitlink、提交和推送。子模块 detached HEAD 是正常状态，不因此创建分支。发布前父仓 gitlink 必须等于已经推送的内核提交，两仓均应 clean。
4. 为本仓创建指向版本提交的标签，推送后核对远端 SHA。不能误把 Release 指向默认分支、未推送提交或其他仓的版本提交，也不能擅自合并主仓开发分支。
5. 通过 GitHub CLI 使用审阅后的正文文件发布；不得用自动生成的提交流水账替代上述内容。示例：

```sh
gh release create v5.1.0 --repo ReliefOSProject/ReliefOS \
  --target FULL_VERSION_COMMIT_SHA --verify-tag \
  --title 'ReliefOS 5.1.0' --notes-file docs/releases/5.1.0.md
```

6. RC 等预发布加 `--prerelease`。发布后用 `gh release view` / `gh api` 回读正文、标签、目标提交、预发布状态和附件列表；已有标签或 Release 不得静默重写，应先检查并按明确授权处理。
7. 源码发布仅含标签、正文和 GitHub 自动源码归档。只有明确选择二进制发布时，才从本次版本提交重新构建并上传产物、SHA256SUMS 和相应归属文件；旧工作区产物不能冒充本版本。
8. 不提交输出目录、缓存、私钥或无关文件。报告时持续明确“VMware 验证未完成”，直到真实完成对应验证；局部历史验证不能当作整版验收。
