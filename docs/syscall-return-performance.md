# 系统调用返回路径与执行锁

后续 Candidate E 的 GPU 空闲清理优化与新一轮测速见 [GPU 空闲清理与管道吞吐](gpu-maintenance-performance.md)。本文保留 Candidate D 当轮的证据与未完成项。

## 改动

普通系统调用此前先取得执行事务锁，完成操作并解锁；`int80_dispatch()` 随后调用 `userland_schedule_from_frame()`，再次取得同一把锁，才判断能否继续运行当前任务。

现在 `syscall_dispatch_frame()` 在原事务内完成该判断。只有现有调度器在 `scheduler_lock` 下确认当前 PID、用户任务类型、RUNNING 状态、本核 reservation、亲和性、有效用户帧、无待加载镜像、无可递送信号且无抢占请求时，才保存返回帧、设置本核 FS base，并返回该任务。架构入口据此省去第二次执行事务。执行锁在进入用户态前仍会释放。

阻塞与可重试 I/O 返回 NULL，保留原指令重试和完整调度；信号、退出、exec 待加载、迁移及抢占也保留完整路径。成功 exec 和 sigreturn 使用它们已恢复的寄存器上下文。系统调用执行期间到达的输入在最终资格判断前处理。没有新增外层递归锁，驱动等待仍在原有的 depth-one 事务中 suspend/resume。

返回路径优化只调整内核内部 C 接口，不改变 Linux 系统调用号、用户寄存器 ABI 或用户态结构布局；没有重生成 ABI golden。定向测试不等于完整 Linux/POSIX 一致性认证。

## 并行构建的 pselect 修复

测试原始基线时，GNU make 4.4.1 的双任务构建停在 jobserver 等待中。暂停私有 QEMU 后检查真实任务状态：两个 GCC 子进程已退出并通知父进程；make 的 SIGCHLD 同时处于 pending 与 blocked，`sigsuspend_active` 却为零，本次系统调用仍是未完成的 pselect6。两核均在 idle，执行锁无人持有。

原因是 pselect 分支只把 `-EAGAIN` 当作内核重试；poll 真正挂起后返回的 `KERNEL_SYSCALL_BLOCKED` 也会进入恢复旧掩码的分支。GNU make 原来阻塞的 SIGCHLD 因此在睡眠期间重新被阻塞，无法中断 jobserver 的等待。[POSIX pselect 规定](https://pubs.opengroup.org/onlinepubs/000095399/functions/pselect.html)要求临时掩码在检查和等待期间生效，到真正返回调用方时才恢复；[GNU make jobserver 文档](https://www.gnu.org/software/make/manual/html_node/POSIX-Jobserver.html)说明了其 FIFO/pipe 令牌等待机制。

修复保留两种内部挂起结果的临时掩码，直到原有信号帧路径或最终返回恢复它。没有改变用户态的 errno、信号编号、syscall restart ABI 或掩码布局。新 host 测试先复现错误，再检查两种挂起、重试与最终返回；真实 guest 测试用无超时的空管道等待、SIGCHLD 和独立 alarm 失败保险，要求子进程退出及时产生 EINTR、执行处理函数并恢复原掩码。原始基线在新增检查处失败，修复后的候选另在 1/2/4 核验证。

## 编译负载下的文件映射缓存

原有文件页缓存固定为 4096 项，即 16 MiB。全部条目被映射占用后，私有映射可以另分配一页，共享映射则返回 EIO。在 VMware 的真实 GCC 负载中，冷启动 Fileman 在共享文件映射缺页时以相同错误退出，未到达窗口就绪状态；该轮明确记为失败，不计入桌面延迟比较。

Host 回归测试在内存充足时准确复现第 4097 个被占用的文件页遭拒。真实 guest 以 POSIX `mmap(MAP_SHARED, PROT_READ)` 映射 6000 页文件，旧内核也在触页时返回 EIO、产生错误信号；映射 VMA 标志与 Fileman 的失败路径一致。修复保留 4096 项作为空闲页缓存预算，超出的正在使用的文件页按需分配 64 项一组的元数据。最后一个引用释放时立即回收扩展页，空元数据块也随之回收。

加载文件和分配元数据在缓存锁外进行，发布时重新检查同一文件与偏移，确保并发加载、两个共享映射及 fork 保持同一物理页。查找、retain、owns 和统计均覆盖扩展条目；没有把共享映射降为独立私有页。Host 的 ASan/UBSan 检查覆盖分配失败清理、重复加载、ELF 边界与私有页兜底；guest 检查覆盖双映射、fork、内容和 munmap。没有修改现有真正耗尽内存时的缺页错误分类策略，亦没有扩大空闲缓存预算。

## 测量方法

本次证据保存在 `out/execution-lock-20261020/`。原始基线包含此前未提交的 AP 定时器与 CPU 统计修复。发现 pselect 问题后，正式性能对照的两端都加入同一个 pselect 修复，单独比较是否省去重复执行事务；不能把基线的无限等待写成编译速度收益，也不把此前定时器修复收益重复计入。

临时诊断内核记录每核、每个调用点的执行锁取得次数、发生竞争次数、等待和持有的原始 TSC cycles。每段只用同核起止计数，拒绝倒退，检查槽位丢失计数为零；没有将跨核 TSC 相减或按未经验证的频率换算微秒。快照在工作负载前后冻结到内存，工作负载结束后才经串口输出。累计最大值不能相减作为分阶段最大值。

临时 `/proc/lock_stat` 使用 QA 自定义格式，不是 Linux lockstat ABI；诊断代码与 proc 入口已从产品源码恢复移除，正式 ELF 另外检查诊断符号和文本不存在。源码、内核、两个 ESP 内核回读及私有测试盘记录 SHA-256。

初测四核管道中，返回调度路径占约 35% 的执行锁持有周期。先试过共享门控返回；其四核吞吐结果不理想，已撤销全部产品改动。最终候选复用系统调用已有的排他事务，保持原来的锁算法。插桩初测中，一份四核样本的事务取得次数由约 105 万降至约 73 万；这只能证明锁事务减少，性能结论采用无插桩内核实测。

GCC 使用官方签名 Alpine v3.24 工具链，隔离安装在私有测试盘 `/opt/qa-toolchain`，不覆盖系统运行库。每轮清理并以 `-O2 -pipe`、`make -jN` 编译上游 zlib 的库、example 和 minigzip，执行 example，并记录库摘要。冷构建包含配置与源文件复制，热构建仍重新编译全部目标，分别报告。插桩 GCC 基线的一个热构建中，mmap 和缺页路径分别占约 51% 和 30% 的执行锁持有周期；返回路径优化不解决这些长事务。

管道正式命令如下，每个环境重复五次，每次传输 4 GiB；吞吐用字节数除以 CLOCK_MONOTONIC 耗时计算，使用十进制 GB/s：

```sh
yes | dd of=/dev/null bs=65536 count=65536 iflag=fullblock status=progress
```

VMware 另测默认 `bs=512` 的原用法，每次限制为 256 MiB，重复三次；它与 64 KiB 的结果分开报告，不把用户态参数变化算成内核收益。

QEMU/KVM 使用同一私有根文件系统、4 GiB 内存，分别比较 1/2/4 vCPU。VMware 使用 2/4 vCPU、2 GiB 内存，检查真实 GCC 后台构建期间的 SVGA3D glamor/GLX、像素回读、Fileman 拖动与 VT 恢复。拖动耗时从宿主机发送 RFB 指针移动到已知完整画面中观察到标题栏移动，包含传输、抓帧和 PNG 保存成本，不是内核输入延迟或本地显示器的帧时间。

开始前既要求进程就绪日志，也要求截图 OCR 看到真实 home 目录内容；日志出现在 `Fl::run()` 之前，不能单凭日志视为窗口已绘制完毕。先通过一次不计时的向上拖动将窗口移离屏幕边缘，再测 40 次交替上下拖动。每次请求 10 像素位移，要求标题栏在正确方向产生至少 5 像素的可见移动，并逐次保存实际位移；这是响应性检查，不是精确定位测试。鼠标先按住 300 ms，再开始计时，连续发送 30 步移动、每步间隔 20 ms，在目标位置松开，然后通过新 RFB 连接取得覆盖完整画面的截图。样本间的 100 ms 间隔不计入耗时。时间包含约 600 ms 的固定输入轨迹及 RFB 开销，不能解释为单个事件的内核响应时间。

早期候选 D 的两次桌面轮次因抓帧和输入工具问题中断，未获得有效拖动样本，保留为排除项：零间隔的按钮边沿被 VMware 合并；随后单个移动事件又只触发 IceWM 的 `handleBeginDrag`，还没有后续事件执行实际移动。源码中 `YWindow::handleMotion` 与 `YFrameTitleBar::handleBeginDrag` 可确认这一区别。修正后的任务专用 RFB 客户端在连接初次建立时要求覆盖全部像素，随后保留已知帧并应用局部更新；模拟协议测试覆盖超过 8 次更新才拼成全帧、后续局部更新，以及拒绝不完整初始帧。两端统一使用同一连续输入轨迹重测，未把失败轮次中较高的小块吞吐挑选为正式结果。

另用标准 Xlib 的 `XQueryPointer`、`XQueryTree`、`XGetGeometry` 校准输入：X11 正确看见 Button1 与指针坐标，但 Fileman 初始框架为 `(52,110,972,632)`，向下移动时被 IceWM 的工作区边缘阻力限制为 `(52,116,972,632)`，其底边恰好为 748。期望固定移动 40 像素的判定因此不成立。正式测量将窗口先移至工作区内部；该校准工具只在独立诊断盘运行，不进入正式性能盘或产品。

随后一次带真实编译的轮次连续完成了 25 次拖动，下一次请求 -10 像素、实际移动 -15 像素。截图显示窗口已移动，没有冻结；因早期条件要求误差不超过 2 像素，该轮在停止编译与 VT 检查之前中断，整轮排除。最终流程保留真实位移，按上述可见响应条件测量，不宣称已验证逐像素指针跟随。所有排除项及原始记录均保留。

双核最终测量轮次完成三次默认块大小管道、18 项绘图/像素检查及 40 次拖动后，停止编译的键盘命令因终端尚未完成焦点切换而只收到后缀，原轮次保留 `completed=false`。仅接受失败之前已经完成的测量数据；编译退出与 VT 在独立的双核运行回归中补验，该回归不重复已经通过的管道与绘图压力测量。新增终端 echo 应答和停止文件存在确认后，真实 GCC 循环完成两轮、`wait` 返回 0，VT2 文本登录与 VT1 桌面恢复均由截图核验。报告分别指向测量记录与补验记录，不把原轮次改写为成功。

缓存修复前的候选 C 用于单独测量返回路径；最终候选 D 再加入动态缓存。VMware 的性能对照两端均加入 pselect 与缓存正确性修复，仅有返回路径优化不同；原来冷启动崩溃的基线另保留失败证据。所有桌面检查都在编译负载启动后冷启动 Fileman，没有通过提前加载窗口避开故障。

测量期间宿主机还运行其他任务，包括不属于本测试的 QEMU；未停止或修改这些任务。宿主机有 12 个逻辑 CPU，另记录了负载样本。吞吐和构建结果为本机本轮观测，保留每次测量，不据少量样本承诺固定收益；尤其冷构建包含配置、文件复制和启动成本，波动不能直接归因于本次代码。

宿主机 `/tmp` 空间不足曾使 VMware 在 guest 启动前崩溃，相关三次尝试全部排除。未清理其他任务的文件。控制器为自己的 VM 使用工作区内临时目录，通过独占创建原先不存在的用户配置传入 VMware，在启动后立即校验并恢复原来的“无配置文件”状态；VM 总在 finally 中关闭。该宿主机修正不属于 guest 内核优化。

新增集成 fixture 编译完整的产品 syscall dispatcher、架构入口和原有用户返回函数，链接真实执行锁，边界依赖由 fixture 提供。修复前先观察到“普通调用再次取得执行事务”的行为失败，修复后验证单事务返回、结果/TLS、信号与输入、I/O 重试、exec/sigreturn 和退出分支。另一并发 fixture 编译真实 scheduler 与锁，检查排队 writer、亲和性、远端抢占和所有权发布。两部分在 host 上分别验证；真实 dispatcher 与调度器的组合由 guest 运行覆盖。

测试输出记录提取源码摘要；ASan/UBSan 用于 host fixture。既有 EEVDF 集成断言、membarrier fixture、SysV SHM fixture、Taskmgr 文案及音频产物失败仍按原清单保留，不借本次优化改动。

真实 guest 的缓存回归源码为 `tools/tests/page_cache_runtime_probe.c`。本轮将其用私有 musl SDK 编译后在启动服务中执行；旧 C 版本触页失败，D 在 1/2/4 核通过双映射、fork、内容和 munmap 检查。在已有 C 工具链的 guest 中也可单独编译该 POSIX 探针运行，约需 24 MiB 临时文件空间。

扩大检查时，`tools/test_linux_memory.py` 另发现两个既有 fixture 签名过期：`physical_pages_test.c` 仍向 `mm_init` 传两个参数，`brk_collision_test.c` 的 `task_shm_map` 少一个参数。两份 fixture 和对应的内核声明均与各自 HEAD 完全一致，证据为 `preexisting-memory-fixture-mismatch.json`；完整 memory suite 仍为失败，不能写成全套测试通过。该套其余用例通过。本次触及的 ELF fixture 补齐日志/分配器依赖并验证新缓存行为，独立目标通过。

## 验证范围

内核编译、定向 host 回归和 QEMU 1/2/4 核的管道、构建及缓存检查通过。完整 memory suite 仍有上述两项既有 fixture 编译错误。

**VMware 验证未完成**：双核候选的 40 次响应检查及独立退出/VT 补验通过，但四核编译负载下的连续拖动检查未通过；本轮没有消除所有桌面交互问题。安装、升级、挂起恢复与长期稳定性也未覆盖，物理硬件未验证。
