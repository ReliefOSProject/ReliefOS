============
在线系统更新
============

``reliefos-update`` 是原生 C 客户端。命令行与 ReliefAPK 的“升级系统”共用
同一套准备、校验、提交和恢复流程。更新范围包括已安装的 ReliefOS 软件包、
上游依赖及应用；普通软件包的查询、单独安装和删除仍使用 APK。

更新器调用真实的 APK 签名验证、依赖求解器、软件包数据库和提交钩子，
不维护平行的包管理数据库，也不通过 Shell 脚本拼接安装命令。
外部软件仍可能依赖尚未实现的 Linux ABI；包升级成功不代表应用运行验证通过。

日常操作
========

先准备更新，再审阅准备结果，最后应用同一个计划::

    sudo reliefos-update prepare
    sudo reliefos-update apply --plan <prepare 返回的计划 ID>
    sudo reliefos-update status

准备过程会联网、验证签名并写入持久缓存，因此需要管理员权限。
计划 ID 是 64 位小写十六进制字符串，只标识本机已经准备好的计划，
不能用网络 URL、任意路径或另一个系统的计划代替。
准备完成不会安装软件包。取消准备或下载失败不会把部分下载当成可安装的软件包。
状态目录仅管理员可读，查询状态也应使用 ``sudo``。

ReliefAPK 的“升级系统”先调用同一客户端准备计划，再在用户确认后应用该计划。
普通桌面会话不必以 root 启动，特权步骤沿用系统的 sudo/root 认证机制。
准备阶段可以取消；进入 APK 提交后应等待明确的完成或失败状态。

软件源和信任
============

软件源沿用 APK 的 ``/etc/apk/repositories`` 及其标准配置目录。
客户端冻结当次使用的源配置、签名索引和信任密钥；保留 world 中的版本限制、
仓库标签及管理员的软件源策略。提交阶段只消费本机准备好的索引和归档，
不重新访问更新后的网站，也不临时选择另一个版本。

生产系统的软件源使用 HTTPS，不能通过关闭 TLS、主机名或包签名验证解决更新错误。
RPR 地址由 ``/etc/reliefos/rpr.conf`` 指定。仓库连通性、索引校验和完整更新
准备是不同的检查：健康探测成功不表示依赖闭包或全部归档可用。

信任公钥来自系统已经安装的 ``/etc/apk/keys``。
配置软件源不会从该源下载并覆盖本地信任公钥；新增或轮换密钥需要独立认证。
管理员修改软件源、密钥、world 或 APK 数据库后，旧计划不能继续提交，
需要重新准备并审阅计划。

持久状态和空间
==============

计划及状态位于 ``/var/lib/reliefos/update``，每个计划有独立缓存和验证记录。
不要手工删除正在准备、提交或等待修复的计划。下载成功的完整归档可以在恢复时复用；
不完整或校验失败的归档不能作为已验证缓存使用。

准备过程检查下载与展开所需空间；内核更新还需要根文件系统及 ESP 的可用空间。
已有内核保留副本、用户模块和管理员文件不会为了腾空间被批量删除。
历史内核和失败计划的空间占用应结合客户端状态及引导恢复需要处理。

更新器通过进程生命周期内的锁串行化操作，状态写入使用临时文件、同步和替换。
APK 的 pre-commit 钩子在其数据库写锁内再次检查准备时的系统身份，
拒绝审阅后发生变化的目标。锁文件、临时文件或日志存在本身不代表更新成功。

中断和失败恢复
==============

遇到断网、进程退出、重启或软件包脚本失败，先查看状态和失败阶段::

    sudo reliefos-update status
    sudo reliefos-update resume

下载阶段可以从持久计划继续；恢复完成并重新获得可应用的计划后，再审阅并提交。
对已经准备好的计划执行 ``resume`` 只返回计划 ID，不会自动安装。
尚未进入包提交的计划可以通过 ``sudo reliefos-update discard`` 作废后重新准备，
原计划的日志和缓存仍保留以供诊断；已经开始提交的失败事务必须先修复，不能丢弃。
如果已经进入 APK 安装阶段，不能假定所有包文件都保持旧版本。
客户端保留失败状态，并提供显式修复入口::

    sudo reliefos-update repair

修复使用该事务已经验证的本机软件包，仍须检查 APK 的退出码、包脚本及最终状态。
计划会在 ``/var/lib/reliefos/update/plans/<计划 ID>/tools/`` 保留当时的静态更新器和
APK 副本。若安装路径下的 ``/usr/sbin/reliefos-update`` 或 ``/sbin/apk`` 在失败后不可用，
可直接运行计划内的恢复客户端；它会检查固定的 APK 和更新器入口，仅恢复缺失或无法运行的工具，
然后从事务中已经验证的签名 APK 重新安装这两个文件的实际所属包。
旧副本只用于启动修复，不能代替数据库记录的新版本；已经可以运行的新版本工具不会被旧副本覆盖::

    sudo /var/lib/reliefos/update/plans/<计划 ID>/tools/reliefos-update repair

如果系统已无法正常启动，可从匹配的 ReliefOS 救援介质挂载根文件系统，例如挂载到
``/mnt/reliefos``，再运行该根目录内保留的静态客户端。``--root`` 必须指向已挂载的目标根；
需要发布内核载荷时，还必须把该系统的 ESP 挂载到目标根下的 ``boot``::

    sudo /mnt/reliefos/var/lib/reliefos/update/plans/<计划 ID>/tools/reliefos-update --root /mnt/reliefos repair

修复失败会继续报告错误，不应通过删除数据库、强制覆盖文件或关闭签名校验来清除错误。
如果失败之后软件源、密钥或 world 已改变，修复会拒绝继续，应先按诊断核对并恢复
原配置。软件包脚本在中断前合法改变这些配置时，同样需要管理员核对，不能把另一组
依赖版本混入原事务。修复允许包数据库因已执行的提交发生变化。

用户态软件包按 APK 的标准方式原地更新。本功能没有创建根文件系统快照，
也不承诺断电后整个用户态自动退回更新前的内容。用户数据和本地配置遵循
APK 文件归属与受保护路径规则；需要合并的配置可能以 ``.apk-new`` 保留。

内核启动确认和回退
==================

内核、initramfs、模块和 ABI 清单作为完整的 ``reliefos-kernel`` 软件包校验。
发布之前保留旧启动载荷和独立模块副本，再切换 A/B 引导记录；正在运行的内核
在重启前不会改变。更新器不在日常更新中重写 BIOS/UEFI 固件加载器。

新内核经过启动确认之后才成为已确认版本。启动尝试耗尽而没有确认时，
引导选择器使用保留的已确认载荷。回退仅覆盖内核、initramfs 和对应模块产品，
不会撤销已提交的普通应用或系统库更新。

缺少匹配的稳定 GRUB 选择脚本、内核包记录或启动确认资源的旧安装，
应使用匹配的安装介质完成引导迁移；客户端拒绝只替换 ``kernel.sys`` 的半套更新。
模块管理参见 :doc:`kernel-modules`。

自动化与验证边界
================

机器接口使用 ``--machine``，例如::

    sudo reliefos-update prepare --machine
    sudo reliefos-update apply --plan <64 位小写十六进制 ID> --machine
    sudo reliefos-update status --machine

准备成功才会输出 ``plan_id=...``。自动化必须同时检查退出状态、计划 ID 和最终状态，
不能依据单条下载或安装日志判断成功。

``--root`` 为显式隔离根测试提供入口；Linux 宿主根目录的修改请求被拒绝。
隔离测试可以使用回环 HTTP 仓库与专用签名密钥；这一测试入口不会放宽
生产系统的 HTTPS 或签名策略。宿主端签名 APK 回归、目标编译、镜像打包、
QEMU BIOS/UEFI 启动与 VMware/物理硬件验证应分别报告，不能互相替代。
